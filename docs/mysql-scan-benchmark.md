# MySQL 普通全量迁移的大表读取对照

本实验用于源库停写或读取静态副本的场景。单任务 MySQL → GaussDB 全量迁移可在高级参数中选择单次扫描，或在启动请求中传 `mysql_read_strategy: "stream"`。省略该字段时使用既有 OFFSET 分页。范围并行仅用于对照试验。分区表使用自己的读取器，CDC 的全量快照使用原有快照事务。

- A 使用原有分页、计数和写入调度。
- B 每表打开一个结果集，分批交给最多 `IntraTableParallel` 个写入任务。写入槽满时会暂停取下一批，每表最多额外持有一个待交付的批次。
- C 只对单列整数主键按 MIN/MAX 拆分闭区间。各区间占用一个表内并发槽，独立扫描和写入。数值范围均分时，稀疏或聚集的主键可能使工作集中在少数区间。无主键、复合主键、其他数据类型以及单路配置使用 B。B、C 都保留迁移后的独立行数核对。

## 复现

在 Linux 或 macOS 上使用专用 MySQL 和 GaussDB 测试实例。MySQL 账号须能创建临时数据库并读取 Performance Schema 的语句摘要，GaussDB 账号须能建 schema、表和任务所需对象。测试生成唯一的源数据库和目标 schema 并在完成后清理。两个 DSN 对应测试实例的连接串。

使用本轮的 GaussDB 505 镜像时，先验证服务器自身可以建立自治会话。该镜像把 Unix socket 放在 `/run/gaussdb`，内部自治连接查找 `/tmp/.s.PGSQL.5432`。本轮在专用容器内使这两个路径指向同一 socket，并配置本地自治账号认证，随后 17 项兼容函数和过程全部完成初始化。

```sh
export DBGOLD_MYSQL_SCAN_SOURCE_DSN='...'
export DBGOLD_MYSQL_SCAN_GAUSS_DSN='...'
export DBGOLD_MYSQL_SCAN_ROWS=1000000
export DBGOLD_MYSQL_SCAN_RESULTS="$PWD/mysql-scan-results.json"
go test ./datamigrate -run '^TestMySQLScan(Comparison|FailureIntegration|UnsignedIntegration)$' -count=1 -timeout 2h -v
```

比较使用同一份源数据，每轮使用新的目标 schema 和 Go 进程。三轮分别按 A/B/C、B/C/A、C/A/B 顺序执行。每批 20,000 行，最多 10 张表并行，表内并发上限 8，两端连接池上限各 50。试验直接调用迁移引擎与真实 GaussDB Writer 的 COPY，`JobMS` 的计时边界是 `Migrator.Run`，API 建连、修复记录与报告持久化在测量范围之外。每轮独立核对行数与完整内容，包括无主键表的重复行。失败注入和无符号主键全域测试单独运行。

## 指标

- JSON 中时间单位均为毫秒。`CopyMS` 是数据阶段的墙钟耗时，`JobMS` 包含准备、建表、复制、后置对象和完整内容校验。`QueueMS`、`FinishMS` 是相对数据阶段开始的时刻，`WallMS` 是该表从领取并发槽到完成的耗时。
- `ReadMS` 和 `WriteMS` 是各工作线程耗时之和，存在重叠。流式读取的 `ReadMS` 扣除了批次交付、等待和同步写入时间。A 的 `OffsetThirdsMS` 是按逻辑页位置分段的平均读取耗时，C 的 `Streams` 列出每个区间实际行数和耗时。
- `SourceRowsExamined` 是按本次源数据库过滤的 `SUM_ROWS_EXAMINED` 在数据阶段的增量，包括 A 为调度执行的首次计数，测量结束于最终校验之前。`SourceTableFetches` 取同一时间窗内该库所有表的存储引擎 `COUNT_FETCH` 增量，计数可包含经缓存满足的取行请求。两端 `Pool` 给出数据阶段的连接等待次数和累计等待时间。
- `PeakRSSMiB` 是独立迁移进程整个生命周期的操作系统峰值，包含内容校验。每种方案都使用相同验证强度。
- `JobHasFailures` 来自真实任务报告的最终状态。基准要求兼容对象、迁移 DDL、复制、行数和逐行内容校验全部通过。

## 2026-11-04 实测结果

MySQL 8.0.36 和 GaussDB Kernel 505.2.1.SPC0800 分别运行在同宿主机的专用 Docker 实例，内存上限分别为 3 GiB、9 GiB。本轮固定数据有 8 张表、1,410,017 行，其中连续整数主键表有 100 万行、稀疏主键表有 250,002 行、宽表有 40,003 行。九次任务均成功，八表行数及完整内容全部匹配，两端连接池在复制阶段均无等待。

以下为每种策略三次运行的中位数。取行次数对应测试 schema 的存储引擎 COUNT_FETCH。

| 策略 | 百万行主表耗时 | 全部表复制 | 引擎全任务（含校验） | MySQL 取行次数 | 进程峰值 RSS |
|---|---:|---:|---:|---:|---:|
| A · OFFSET | 1.904 s | 1.904 s | 7.336 s | 29,080,031 | 276 MiB |
| B · 单次扫描 | 0.461 s | 0.886 s | 6.265 s | 1,410,017 | 255 MiB |
| C · 范围并行 | 0.603 s | 0.783 s | 6.276 s | 1,410,056 | 283 MiB |

A 的百万行主表按页位置分三段，平均读页耗时的中位数从 181 ms、261 ms 增至 397 ms。B 将源端取行次数降低 95.2%，全部表的复制阶段缩短 53.4%，含内容校验的任务总耗时缩短 14.6%。切换到 B 后，最后完成的变成了 40,003 行的宽表；数据量和行宽会改变拖尾位置。

C 的复制阶段更快，但稀疏表的八个区间中有四个为空，最重的区间包含 187,500 行。该表耗时中位数为 694 ms，B 为 228 ms。C 三轮整项任务分别为 6.636、6.276、6.157 s，B 为 6.265、6.313、6.214 s，未显示稳定的端到端优势。用户入口提供 B，C 保留作实验。生产跨机延迟、目标写入能力和业务表行宽都可能改变上述数值。
